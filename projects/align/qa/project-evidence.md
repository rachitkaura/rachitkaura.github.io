# Structured project evidence

Candidates use Profile → Work examples to create a private, reusable example. A three-step editor captures project type, context and optional dates, scope, ownership, personal contribution, a decision and its trade-offs, outcome, measurement, limitations, optional tools/assistance and supporting evidence. The desktop preview and mobile disclosure use the same renderer as the shared example.

New examples require explicit permission and confidential-information removal confirmation. HTTPS links are validated without fetching their contents. Descriptions support redacted work and private-work alternatives; this feature does not upload or inspect confidential source documents. Simulations and recreated artifacts are clearly labelled. Older cards remain readable and can be upgraded without inventing missing details.

Examples remain private until the candidate shares a selected card with an active mutual match. Public profile excerpts require separate consent and include project type/ownership so simulations cannot masquerade as employment. Excerpts exclude artifact links, evidence descriptions and application-specific checks. Changing the original removes the excerpt until republished.

Hiring teams can record four bounded checks: employment dates confirmed, artifact reviewed, contribution corroborated and capability demonstrated. A check requires the exact scope, source, remaining uncertainty and a completed-check attestation; contribution corroboration also requires a candidate-permission attestation. The application supplies the company and access scope; authenticated headers supply the reviewer display name, and the server supplies the timestamp. The authenticated reviewer account ID is retained in storage without exposing that internal ID in candidate-facing records or exports. UI copy identifies these as hiring-team records rather than independent Align certifications. Each type has one current record per shared application; a team can replace or remove it. This is not an immutable historical audit log or an automated background-check service.

Checks do not affect fit scores or discovery. Server-generated revisions reject stale reviews even if timestamps coincide, and a conditional database update protects against a concurrent edit or review. Editing a card clears all of its shared checks, discussion labels and follow-up notes. Revocation, withdrawal, closing and blocks prevent future access. Candidate-consented handoff exports include only that application's shared example and checks.

The additive migration `0006_project_evidence.sql` adds a non-null JSON-text checks column with a constant empty-array default. All migrations were applied to a clean local preview database and exercised in real SQLite integration tests. Production migrations are applied by Sites publication.

## Verification

- `node tests/project-evidence.test.cjs`: 149 checks passed for structured/legacy validation, safe URLs, metadata injection prevention, permissions, authenticated reviewer attribution, narrow checks, consent, stale card versions, edits, simulation labels, per-company isolation, exports, revocation and offline demo persistence.
- Existing suites passed: 209 demo assertions, 102 focused-hiring assertions, 111 document-sharing assertions, 22 work-proof cases, 13 application-source cases and swipe, scrolling, inbox, outbox, feedback, navigation and guided-demo regressions.
- Candidate browser flow passed: create a complete private example through all three steps, explicitly share with one matched employer, review the shared example as that employer, record a scoped artifact check, and inspect its reviewer, source, limitations and timestamp.
- The initial accessibility pass found repeated region names when multiple examples were shared. Evidence groups now identify their project and do not introduce duplicate region landmarks. Input alignment, select labels, disabled saving controls and editor and check-form focus restoration were also corrected during QA.
- Two clean UI/accessibility loops passed eight evidence scenarios each: all editor steps, small phones, desktop, 200% text, dark mode, candidate-visible checks and the employer recording form. Two wider regression loops passed twelve viewport cases each, including mobile/landscape/desktop swipe controls, Inbox and candidate comparison. Reports are in `evidence-ui-round-{1,2}.json` and `evidence-viewports-round-{1,2}.json`. All forty final cases had zero axe violations, failed contrast reviews, app errors or horizontal overflow; fields and swipe controls stayed inside their applicable viewport bounds.
- Keyboard checks after the final fixes confirmed that a saved check returns focus to Record an evidence check, a saved example returns focus to New work example, and editing clears the previous shared checks.
- Two performance loops passed all operation and production asset budgets, including the new scoped-check mutation. Reports are in `evidence-performance-round-{1,2}.json`. These are local diagnostic measurements, not production Core Web Vitals.
- Reproducible browser harness: `evidence-audit-harness.html`, served temporarily as `public/__qa-audit.html` with axe-core. Temporary public QA assets are removed before the production build.
- Browser measurements use the development preview. Performance budgets use the actual demo engine and production assets. Automated scans do not constitute a complete assistive-technology certification.
